# Overengineering Review Standards

This document defines how to spot Python code that is more complex than the
problem needs. It serves as both a human-readable reference and the automated
reviewer's criteria.

AI assistants tend to produce more code than was asked for: extra layers,
extra options, extra safety nets, extra files. Each addition looks reasonable
alone, but together they make the change harder to read, test and maintain.
The goal here is the smallest change that does the job.

**Scope:** any `.py` file added or modified in this PR.

**Out of scope:** `_version.py` (auto-generated by hatch-vcs), `__pycache__/`,
`.venv/`, `*.lock`.

## The core test

For every piece of new code, ask:

1. Does the purpose of this PR need it?
2. Is there a caller today that uses it?
3. Could it be deleted, or replaced with something simpler, with nothing lost?

If the answer to 1 or 2 is "no", or the answer to 3 is "yes", it is a
candidate. Code written for a future need that does not exist yet should be
added when that need arrives.

## 1. Speculative Generality

Abstractions are worth their cost once there is more than one real use. Before
that they are guesses.

### One implementation does not need an interface

**Bad — abstract base class with a single subclass:**
```python
class ReportWriter(ABC):
    @abstractmethod
    def write(self, report: Report) -> None: ...


class CsvReportWriter(ReportWriter):
    def write(self, report: Report) -> None:
        report.to_frame().to_csv("report.csv")
```

**Good:**
```python
def write_report(report: Report) -> None:
    report.to_frame().to_csv("report.csv")
```

The same applies to `Protocol` classes, registries, plugin systems and
factories that hold a single entry.

### Unused parameters, options and flags

**Bad — nothing passes `region` or `fmt` except the defaults:**
```python
def load_orders(path: Path, region: str | None = None, fmt: str = "csv", **kwargs) -> pd.DataFrame:
    return pd.read_csv(path, **kwargs)
```

**Good:**
```python
def load_orders(path: Path) -> pd.DataFrame:
    return pd.read_csv(path)
```

Check callers in the diff and the surrounding module. An option nobody sets is
an option nobody has tested.

### Patterns used for a trivial operation

Strategy, Builder, Command and dependency-injection containers are heavy for
what is often a function call.

**Bad — builder for three fields:**
```python
class QueryBuilder:
    def __init__(self) -> None:
        self._table = ""
        self._limit = 100

    def table(self, name: str) -> "QueryBuilder":
        self._table = name
        return self

    def limit(self, n: int) -> "QueryBuilder":
        self._limit = n
        return self

    def build(self) -> str:
        return f"SELECT * FROM {self._table} LIMIT {self._limit}"
```

**Good:**
```python
def build_query(table: str, limit: int = 100) -> str:
    return f"SELECT * FROM {table} LIMIT {limit}"
```

### Pass-through wrappers

A function or class whose only job is to call another one with the same
arguments adds a hop for the reader and nothing else.

**Bad:**
```python
def get_user(user_id: str) -> User:
    return user_repository.get_user(user_id)
```

**Do not flag:** a wrapper that adds behaviour (translating errors, adding
logging context, narrowing a type) or that deliberately isolates a third-party
API behind one module.

## 2. Scope Creep

### Code beyond what the PR set out to do

Compare the diff to the PR title, description and linked issue (if available/relevant). Flag changes
that go further than that stated purpose:

- New CLI options, output formats or endpoints nobody asked for.
- New modules, layers or packages for a single caller.
- Refactors, renames or reformatting of code the PR otherwise does not touch.
- Several features in one change when each could be reviewed alone.

**Bad — a bug fix PR that also adds a config system:**
```python
# PR: "Fix crash when the report has no rows"
def build_report(rows: list[Row], settings: ReportSettings | None = None) -> Report:
    settings = settings or ReportSettings.from_env()  # new, unrelated to the fix
    if not rows:
        return Report.empty()
    ...
```

**Good — the fix alone:**
```python
def build_report(rows: list[Row]) -> Report:
    if not rows:
        return Report.empty()
    ...
```

Unrelated improvements may be good ideas. Suggest splitting them into their
own PR or a GitHub issue.

## 3. Defensive Code That Cannot Trigger

Safety nets belong at the edges of the system, where input is not under your
control. Inside it, they hide real bugs and clutter the logic.

### Checks the types already guarantee

**Bad:**
```python
def total_cost(items: list[Item]) -> Decimal:
    if items is None:
        return Decimal(0)
    if not isinstance(items, list):
        raise TypeError("items must be a list")
    return sum((item.cost for item in items), Decimal(0))
```

**Good:**
```python
def total_cost(items: list[Item]) -> Decimal:
    return sum((item.cost for item in items), Decimal(0))
```

### Try/except around code that cannot fail

**Bad:**
```python
try:
    names = [user.name for user in users]
except Exception:
    names = []
```

Catching broad exceptions to "be safe" also hides failures. Handle the
specific error that can occur, and only where it can occur.

### Retries, fallbacks and defaults with no known failure

**Bad — retry loop around a local, deterministic function:**
```python
for attempt in range(3):
    try:
        return parse_config(path)
    except ValueError:
        time.sleep(1)
```

Retries need a transient failure to retry (network, throttling). Fallback
values that quietly replace a failure need a reason to exist.

### Validation repeated at every layer

Validate once, at the boundary, then pass the validated object inward.

**Bad — the same checks in the route, the service and the repository.**

**Good — a Pydantic model validates at the route; inner layers trust it.**

**Do not flag:** validation of user input, request bodies, environment
variables, files and responses from external APIs. These are real trust
boundaries.

## 4. Reinventing What Already Exists

Check whether the standard library or a dependency already in `pyproject.toml`
does the job.

**Bad — hand-rolled helpers:**
```python
def read_file(path: str) -> str:
    f = open(path)
    try:
        return f.read()
    finally:
        f.close()


def group_by_status(records: list[Record]) -> dict[str, list[Record]]:
    groups: dict[str, list[Record]] = {}
    for record in records:
        if record.status not in groups:
            groups[record.status] = []
        groups[record.status].append(record)
    return groups
```

**Good:**
```python
def read_file(path: Path) -> str:
    return path.read_text()


def group_by_status(records: list[Record]) -> dict[str, list[Record]]:
    groups: defaultdict[str, list[Record]] = defaultdict(list)
    for record in records:
        groups[record.status].append(record)
    return groups
```

Common cases: `pathlib`, `collections` (`defaultdict`, `Counter`),
`itertools`, `functools` (`cache`, `partial`), `dataclasses`, `contextlib`,
Pydantic validators instead of manual type checks, `boto3` paginators instead
of manual `NextToken` loops, and pandas built-ins instead of row-by-row loops.

## 5. Heavier Than Needed

### A class where a function would do

A class with no state beyond its constructor arguments and one public method is
a function.

**Bad:**
```python
class ReportFormatter:
    def __init__(self, currency: str) -> None:
        self.currency = currency

    def format(self, amount: Decimal) -> str:
        return f"{self.currency}{amount:,.2f}"
```

**Good:**
```python
def format_amount(amount: Decimal, currency: str = "£") -> str:
    return f"{currency}{amount:,.2f}"
```

### Async with nothing to await

**Bad:**
```python
async def build_title(name: str) -> str:
    return f"Report for {name}"
```

Use `async` where the function awaits I/O, or where a framework requires it.

### Layers of tiny single-use helpers

Splitting is good when a helper has a clear name and meaning of its own. It is
noise when a reader has to jump through four one-line functions, each called
once, to follow a simple flow.

**Bad:**
```python
def process(order: Order) -> Receipt:
    return _make_receipt(_apply_discount(_get_total(order)))
```
where each helper is a single line and is used nowhere else.

### Unneeded intermediate structures

**Bad — build a dict, then a list, then loop it:**
```python
mapping = {item.id: item for item in items}
ids = list(mapping.keys())
for item_id in ids:
    print(mapping[item_id].name)
```

**Good:**
```python
for item in items:
    print(item.name)
```

## 6. Typical AI-Generated Excess

Assistants often leave behind patterns like these. They need a second look
before merge.

- **Helpers written but never called**, or parameters and return values left
  over after the design changed.
- **Near-identical functions** generated side by side instead of one
  parameterised function.
- **Placeholder hooks** such as "extend here in future", empty `on_*` callbacks,
  or `__all__` and `__init__` re-exports that nothing imports.
- **Over-wide error handling** that logs and re-raises at every level, so one
  failure produces four log lines.
- **Excess logging** that narrates every step (`"Starting X"`, `"Finished X"`)
  of ordinary code.
- **Config for constants** that never change: environment variables, settings
  classes or YAML files for a value used once.
- **Test-only code in production paths**, such as flags that exist only so a
  test can reach a branch.
- **Large generated docs or markdown** for a small change, such as a README
  section longer than the code it describes.
- **Type machinery with no payoff**: `TypeVar`, `Generic`, `overload` or
  `TypedDict` layers for a function with one concrete use.

**Bad — never called, plus a speculative hook:**
```python
def _normalise_name(name: str) -> str:  # no callers in the codebase
    return name.strip().title()


def export(report: Report, on_export: Callable[[Report], None] | None = None) -> None:
    ...  # on_export is never passed anywhere
```

When the diff does not show whether something is used, say so and ask rather
than asserting.

## 7. How to Raise a Finding

Overengineering is a judgement call, and the reviewer can not see the intent
behind the change.

- Raise every finding as a **Suggestion**, never Critical.
- Name the specific code, say what could be removed or simplified, and show the
  simpler version when it is short.
- Prefer a question where intent is unclear ("Is `fmt` needed? No caller sets
  it").
- Group related findings (for example, an interface plus its single
  implementation) into one item.
- Keep it proportionate. A few well-chosen findings beat a long list of small
  ones.

## 8. Anti-Patterns to Flag

- Abstract base class, `Protocol`, factory or registry with a single
  implementation
- Parameters, flags, `**kwargs` or config options no caller uses
- Builder, Strategy or Command patterns around a trivial operation
- Wrappers that only forward to another function
- Changes beyond the PR's stated purpose (features, refactors, new layers)
- `isinstance`, `None` or emptiness checks that the type hints already rule out
- `try/except` around code that cannot fail, or a broad `except` used as a
  safety net
- Retries or fallbacks with no known failure to handle
- The same validation repeated at several layers
- Hand-rolled code for something the standard library or a current dependency
  provides
- A class with one method and no state; `async` functions that await nothing
- Chains of single-use one-line helpers
- Helpers, parameters or hooks that nothing calls
- Near-identical generated functions that should be one
- Settings or environment variables for values that never change

### Do NOT flag

- An abstraction with two or more real implementations or callers in the
  codebase
- Validation and error handling at genuine trust boundaries (user input,
  external APIs, environment variables, files)
- Complexity that the PR description or a code comment explains. Raise at most a
  **Suggestion** and leave the final decision to a human
- Code a framework requires, such as Dash callback signatures, Pydantic models,
  CDK constructs, or an `async` handler the framework awaits
- A wrapper that adds real behaviour or isolates a third-party API
- Small, well-named helpers that make a long function easier to read
- Retries around network or throttled calls such as AWS and HTTP requests
- Comment quality, docstring content, TODOs, naming and duplicated code. These
  are covered by separate review criteria
- Unused imports and other issues ruff already reports
- Test files (`test_*.py`, `conftest.py`) and generated code
